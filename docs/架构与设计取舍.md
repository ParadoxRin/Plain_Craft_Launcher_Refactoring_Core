# 架构与设计取舍

本文说明0.37的实现组织和主要选择。约束以[架构规范v1.4](architecture/PCL-Mac架构规范.md)为准；落地证据和剩余债务分别见[验收报告](0.36-Iris环境卸载与世界验收.md)及[技术债](architecture/技术债.md)。这里不把目标架构直接等同于所有现存代码已完成改造。

## 1. 要解决什么问题

Windows PCL的界面、系统能力和执行流程不能直接搬到macOS运行。Mac还需要处理大小写保留路径、Apple Silicon原生库、Java架构、钥匙串、窗口/Dock以及长期游戏进程的生命周期。

如果把每个功能直接写进窗口，下载、安装和账户规则会随着页面复制，关闭窗口还可能丢失后台任务。项目因此保留现有可复用核心，逐步将执行权移入Host，再通过契约对接Avalonia界面。已有InstallOperations/VersionInstaller继续承担安装，避免迁移期间同时重写业务和UI。

## 2. 当前职责与依赖

| 部分 | 负责什么 | 不应负责什么 |
|---|---|---|
| Desktop | 控件、输入、导航、展示、窗口生命周期 | 直接安装、唯一的依赖求解或凭据读写 |
| Contract | 请求/结果/事件、能力和版本约定 | 平台API、业务状态存储 |
| Client | 请求关联、RPC、订阅、会话重连 | 决定加载器或Java兼容策略 |
| Host | 组合根、独占数据根、协议入口、执行者生命周期 | 反向依赖UI展示 |
| Application | 用例编排、授权协调、任务状态/取消/映射 | 具体窗口实现 |
| Domain | 显式输入上的约束、规则和纯解析 | 访问网络、磁盘、进程或探测宿主 |
| Ports | 外部能力的行为约定 | 具体平台实现 |
| Core / Adapters | 既有业务执行与网络/文件/凭据/进程适配 | 在迁移入口绕开Host重新授予UI写入权 |

规范的编译依赖向核心收拢：`Shell → Contract/Client`，`Client → Contract`，`Application → Contract/Domain/Ports`，`Ports → Domain`必要值类型。**不存在Domain → Ports**，避免程序集环。Application取外部数据再交给Domain，不给Domain注入文件系统或网络服务。

当前Host组合Core中的适配实现；部分既有服务仍保留在Core内，后续按用例整理。Desktop到Host的项目引用属于构建/打包依赖，不能理解成可在展示代码调用Host实现。CLI仍可直接复用核心，不能据此给Desktop开例外。

实际引用和符号由[ArchitectureGuard](../scripts/ArchitectureGuard/Program.cs)检查；“项目能编译”以外，还要通过用例追踪确认业务规则没有只存在于UI。

## 3. 为什么三个平台用原生UI，而核心独立共享

目标是macOS使用SwiftUI，Windows和Linux分别使用本平台原生UI库；后两者的具体库尚未选定。这样各平台可以采用合适的窗口、导航、输入和系统交互，同时共用安装、账户、资源、依赖求解与启动核心。这是Desktop/Core分离的首要动机。

当前Pcl.Desktop仍为Avalonia，承担迁移过渡和功能对照。SwiftUI是确定的Mac目标，不是可选设想；但本仓库0.36尚未完成SwiftUI替换，也没有已验收的Windows/Linux原生客户端。Windows风格页面结构用于当前功能核对，不强制三个原生界面复制相同控件与窗口布局。

三个Shell通过各自Client接入同一版本化Host协议；共享的是数据、事件、错误、取消和恢复语义。SwiftUI不直接引用.NET程序集，需要Swift协议适配和一致性测试。业务规则与凭据执行留在核心/Host；Host和Adapters按目标平台构建部署，不把当前Mac二进制直接分发给三个系统。

独立Host让UI与执行生命周期解耦：视图关闭不等于任务取消，UI短暂断连后可以查询现有操作，而不是再安装一遍。凭据、下载器和进程句柄只有明确拥有者，减少多窗口创建重复服务、双重释放及并发写入问题。

代价是需要处理协议、Host部署、断连、事件水位及退出竞态。项目先完成同进程入口与组合根，再引入操作模型和独立Host，没有以“将来可能多客户端”为由一开始就承担全部IPC复杂度。

## 4. 为什么用Contract、operationId和持久化回执

Contract隔离Shell与内部对象，避免窗口拿到任意服务、路径权限或认证会话。内部Port可以使用强类型/流，跨进程边界只暴露必要数据；大内容通过受控blob资源分块/分页，避免无限扩大协议帧。

长安装不是一个等待数小时才返回的RPC。受理后产生operationId，客户端再查询快照、订阅进度或取消；幂等键将重试关联到同一操作。幂等键的作用域和参数一致性必须检查，不能只用版本号作为所有安装的唯一标识。

会话恢复与任务续做分开：同一Host存活时恢复状态展示；Host退出后通过receipt检查文件、计划及阶段，再决定能否继续。receipt记录恢复所需数据，日志另行限长保存。超时并不证明后台已停止，不能因为客户端超时就再启动重复写入。

这套机制不意味着所有任务都能任意位置续做。现有原版/支持加载器可校验并重执行相应安装阶段，整合包与资源任务仍有需重新发起的范围；详见[NET-011等剩余项](0.36-剩余清单.md)。

## 5. 为什么严格区分退出、取消和独立游戏

Minecraft是长生命周期进程。启动应返回可追踪句柄，而不是阻塞到退出；短命令执行与游戏托管因此分离。UI退出策略、Host关闭和“游戏继续独立运行”是不同选择。

正常关闭先停止会话重连等监视器，再按策略处理任务和资源，避免窗口关闭后重连任务又拉起Host。调用者释放自己的引用，不额外释放另一个组件拥有的HttpClient或进程资源。

实例写入期间和游戏运行期间必须实施Host端互斥，不能只禁用按钮。数据根以OS独占锁保持所有权；不能按PID/心跳/TTL猜测后抢锁。文件还在不等于锁还被持有，反之删除锁文件也不能合法绕过正在使用的锁。

## 6. 为什么卸载需要归属、依赖和事务三重检查

“下载过某个JAR”不能证明以后可以删除它：它可能被其他模组共享、被用户修改，或早在本次环境安装前就已存在。

Iris安装因此记录安装前状态，只对本次引入的文件建立归属，完成后固定哈希。正常资源安装登记其他用途。卸载预览综合实际Fabric元数据、嵌套模块、别名、版本约束及保留组件计算可删除集合。

实际测试曾发现：Iris内嵌API与独立Fabric API提供同一依赖时，保留全部提供者会错误阻止卸载。现在优先复用已保留的匹配提供者，再优先保留非Iris提供者；共享Sodium和实际Sodium Extra用例已验证。

确认弹窗只展示Host计划。用户确认后Host重验指纹，备份组件和前后清单，刷盘并写提交意图，然后逐文件删除/原子替换。进程中断后先核验备份和剩余文件再续做；现场有新依赖、被改动文件或损坏备份就停止，而不是完成一半后假报成功。

代价是保守：旧版/手动环境没有可信安装前记录时不自动追认；修改、禁用或改名导致身份变化时拒绝；Fabric依赖覆盖配置未被完整解释时不自动卸载。失败安装的外部用途记录也可能多保留文件。这些限制比误删用户文件更容易恢复，但仍需在后续逐项补齐支持。

## 7. 为什么采用副本修改和明确拒绝

复杂加载器和整合包包含生成文件、继承关系、模组与用户配置。任意原位修改难以保证完整回滚，当前优先在新副本重建组件、固定源/目标和检查指纹，保留原实例及来源记录。

副本确认不是绕过校验的授权：即使用户关闭提示，Host仍要检查路径占用、源变化及实例状态。原位修改、任意继承链、自定义客户端和配置三方语义合并仍列为缺口，不能用“已经有复制功能”替代。

## 8. 为什么不统一隐藏兼容性限制

Apple Silicon Java和Mach-O原生库需要实际架构核对；版本目录或元数据允许下载不等于游戏一定能在Mac运行。宿主平台探测与目标平台规则要分开，禁止UI按当前操作系统猜Java或加载器策略。

依赖元数据不能覆盖模组的动态代码和自行下载的原生库。求解预算达到上限要报告“未判定”，不声称“无解”。Forge Quick Play等已复现问题保持显式限制，直到取得针对性修复与实测证据。

同理，账户API成功、标题渲染、世界进入和用户确认是不同证据层级；不会把一份运行日志扩写成全部版本、所有Mac或完整PCL功能已经验收。

## 9. 设计决策的后续约束

保持微软与离线登录、皮肤和独立游戏行为；保留原作者赞助与正版购买劝导，不提供赞助解锁；不增加矩阵子进度或通过分类调整关闭实现缺口。新能力应优先复用已有执行链，并在同一用例中覆盖取消、冲突、恢复、关闭和单一释放责任。

详细历史决策及三平台原生Shell决策DEC-007及规范约束见[完整规范](architecture/PCL-Mac架构规范.md)，未完成的内部整理见[技术债](architecture/技术债.md)。

## 10. 0.36.1 启动劝导为何跨两层

Domain以显式输入计算购买和试玩规则，Core应用服务读取匿名正版验证标志，Host提供game.guidance。Shell负责展示与确认；GameLaunchOperationService将确认纳入幂等指纹，执行器在准备Java和创建进程前检查。这样更换SwiftUI不会丢失规则，取消弹窗不会产生启动任务，同一受理请求不会重复启动。匿名标志不包含身份或凭据；认证仍由IAccountSecrets和Host负责。

产品显示名改变，但数据目录、bundle标识和钥匙串命名保持稳定，避免改名导致已有登录和存档看似丢失。公开源码要求尚未满足，私有开发状态明确显示在关于页与README。

## 11. 0.37 为什么共用规划而保留事务安装器

过去单项、批量和整合包分别求解，容易对同一组文件给出不同结果。现在它们提交相同的锁定根和实例上下文给 ResourceDependencyPlanner；规划只在私有快照中执行候选安装，并校验原目录的资源、清单、版本与覆盖文件未变化。实际提交仍复用 ResourceInstaller 和既有整合包 pending 发布流程，避免为统一规则重写可靠性边界。

完整本地包先离线验证；只有需要补前置时才按哈希向目录查询版本。文件身份与依赖声明分别处理，未知本地 JAR 保持锁定，不凭名称猜项目。搜索有明确预算，不能在超限后冒称无解。代价是快照复制、重复元数据读取和候选下载开销；尚未引入共享无锁快照或任意 SAT 求解。
