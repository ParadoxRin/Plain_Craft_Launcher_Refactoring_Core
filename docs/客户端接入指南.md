# 自定义客户端接入指南（main；0.41.0 后增量）

目标：使用任意适合的平台 UI 组件，复用 Host 中的安装、账户、资源、实例和启动能力。已有 Avalonia/.NET Client 和[可独立运行的最小命令行客户端](../examples/Pcl.MinimalClient/README.md)作为参考。最小示例不引用 Core，并配有真实 Host 契约验收；这仍不是已发布的 Swift SDK 或 Windows/Linux 完整实现。

先运行最小示例，实际观察 operationId、取消终态、同 Host 重连及新 Host 续做；命令与构建方式见示例 README，当前证据见[最小客户端验收](最小客户端与Host契约验收.md)。示例的 restart 是正常关闭，不是崩溃；崩溃仅由隔离验收程序模拟。

## 入口与阅读顺序

1. `src/Pcl.Contract`：请求、结果、事件、稳定 ID、错误及能力。历史命名空间含 Pcl.Core.Contracts，不代表需要引用 Core DLL。
2. `src/Pcl.Client/HostClient.cs`、`HostSubscriptions.cs`、`LauncherSession.cs`：协议、订阅/快照、重连、账户与游戏观察的参考实现。
3. `src/Pcl.Host/Program.cs`、`PrivatePipeServer.cs`、`Composition/HostRuntime.cs`：协议分发、私有会话及资源所有权。
4. `src/Pcl.Desktop/Bootstrap` 和导航/窗口生命周期实现：借鉴接线方式，布局和组件可以替换。

.NET 客户端只引用 Pcl.Contract 与 Pcl.Client；不要引用 Core/Application 来省略 RPC。Swift 或其他语言实现等价的数据映射和传输。当前尚无覆盖全部消息的外部 SDK/schema 生成流水线，应结合 Contract、Host 分发与契约测试核对字段，不能把文档示意当作新增 API。

## 协议与最小链路

现有协议是 PCL 自定义 RPC v1，UTF-8 NDJSON，不声明 JSON-RPC 2.0 兼容。每帧单行，帧大小和能力以 hello 返回为准；Host stdout 专用于协议，stderr 为诊断。桌面默认私有管道，stdio 用于直接进程接入/测试；完整重连需要实现私有会话身份和 attach，不是重新启动一个写同一数据根的 Host。

stdio 模式先发送下列 hello。默认私有管道模式必须先 session.attach（ClientIdentity 的 clientId/processId/startedUtcTicks，以及 Linux 上必需的 linuxStartTicks），收到 attachment 后再发送 hello，不能颠倒。握手与请求 ID 的完整约束见[架构规范 §7](architecture/PCL-Mac架构规范.md#7-命令与进程外协议)。

Linux 的 `linuxStartTicks` 是 `/proc/<pid>/stat` 第22字段的原始无符号整数（开机以来的时钟 tick），不是 UTC ticks，也不是毫秒。Host 精确比较此值，缺少/错误时拒绝，不按 PID 或时间容差回退；Client 和 Host 必须一同更新。`startedUtcTicks` 仍保留 UTC .NET ticks 的原含义，Windows/macOS 继续精确校验此字段。旧 Linux 客户端仅发送 UTC 值的握手不再被接受，私有管道模式需要这一出生证明；已发布 v0.41.0 的 Mac 包不在本次更改范围。非 .NET 实现不要把进程名里的空格/右括号当成 stat 字段分隔；参考 `SharedProtocol/ProcessBirthIdentity.cs`。

hello：

```json
{"protocolVersion":1,"id":"0123456789abcdef0123456789abcdef:1","method":"host.hello","params":{"minimumVersion":1,"maximumVersion":1}}
```

读取 `protocolVersion`、`hostInstanceId`、`capabilities`、`maximumFrameBytes` 与可选 `installationTarget`。同一连接使用 32 位 GUID 前缀 + 冒号 + 从 1 连续递增的序号，按发送锁顺序分配；重连使用新前缀，迟到响应不得完成另一次请求。不要假定请求完成顺序等于发送顺序。

按当前 Contract 构造参数，逐步跑通：

| 用例 | 当前方法/入口 | UI 必须处理 |
|---|---|---|
| 账户 | account.snapshot、account.login.begin/get/cancel；工作区离线账户操作 | 设备码/网页确认、等待/取消/过期；不接收原始令牌 |
| 安装 | version.install、operation.get/cancel | 受理结果、错误码、阶段、取消后的真实终态 |
| 资源/设置/实例 | page.begin/get/cancel，method 由 WorkspaceOperations 定义 | 不透明选择 ID、计划确认、过期重新预览和冲突；不能直接写磁盘 |
| 事件 | event.subscribe/unsubscribe | 先缓冲订阅再取快照；按序号去重，缺口/背压时重取权威状态 |
| 游戏 | game.guidance、game.launch、game.get/stop/details | 展示规则并取得明确确认；启动操作完成不等于游戏退出 |
| 大资源 | blob.open/read/page/close | 有界分块、EOF/过期、读取后关闭，不用任意绝对路径代替句柄 |

安装 params 必须按 InstallCommand 嵌套 installation（gameVersion/loader/target），不要使用旧的扁平参数。事件为 event.changed，params 为 HostEvent，含 snapshot；RPC 失败当前仅 error.code，没有通用 detail/retry 字段。登录 key/remember、账户状态与外观任务按各自契约处理，不统一套用安装重放。第三方密钥的受控输入可走 workspace.secret，随后只传短时句柄；微软令牌不得返回客户端。

`version.install.v3`、`game.launch.v2` 等是能力标识，不是方法名；实际方法仍是 version.install/game.launch。不同方法的错误和参数以当前 Contract 为准。

## 不能放入 UI 的实现

Java/加载器匹配、依赖规划、包检查、下载校验、安装提交、游戏权限判定和凭据刷新必须留在核心。UI 可做格式提示，但 Host 必须权威校验。客户端短暂超时不代表操作停止；重试保持原幂等键和参数，终态后新尝试才换键。先查询同一 operationId，不能通过新键制造重复安装或重复游戏。

视图取消只释放本视图订阅；用户主动取消后台操作时另发取消请求。Host 重启后不擅自重放所有任务，读取状态和支持的安全续做路径。游戏独立运行时退出 UI/Host 不应误杀游戏，必须实际验证。

## 三平台适配与自定义范围

可替换主题、控件库、窗口/页面布局、导航、语言和展示缓存。原生文件选择器与窗口装饰由 Shell 处理。凭据、路径卷能力、文件锁、进程脱离、Java/natives 和系统集成由各平台 Host/Adapter 负责；当前组合根绑定 Mac Keychain，Windows/Linux 需要真正实现和测试，不能直接复制该绑定。

自定义客户端保留 PCL 署名/赞助链接及购买/赞助劝导、Windows 蓝色和无赞助解锁限制；不得因“自定义界面”删除这些规则。MIT 范围见 LICENSE.md，不将上游衍生内容自动改成 MIT。

## 最小验收清单

- 请求/响应、未知字段/能力、版本不兼容、帧限制、迟到响应与结构化错误。
- 安装→取消→同 Host 会话重连→Host 重启后安全续做→启动；每段记录真实执行范围。
- 订阅期间更新、断连/背压、快照合并，无重复副作用或事件丢失导致永久卡住。
- 登录取消/刷新、UI 重开、凭据不进入 DTO/日志/设置；真实账户测试与替身分开。
- 关闭页面、退出客户端、托管游戏退出、独立游戏继续运行与数据根锁再获取。
- 目标平台真实 Java、natives、文件大小写/权限和游戏世界保存；Mac 证据不替代 Windows/Linux。

优先做一个完整的安装/启动页面贯穿链路，再扩展其余 UI。不要先复制全部界面，然后为缺少的执行能力建立另一套业务实现。
