# PCL Mac 架构规范

版本：1.4\
日期：2026-10-26（Australia/Sydney）\
性质：后续增量重构的实施规范\
依据：已落盘的《分层架构实施规范 v2》、本轮评审共识、当前仓库实际调用链。

本规范替代 v2 中仍有歧义的实施表述。v2 原文件保留为讨论记录；本规范不表示现有代码已经完成分层，也不追认历史功能或测试状态。

## 1. 目标与适用范围

目标是让 macOS、Windows 和 Linux 各自使用平台原生 UI，共享安装、资源管理、账户、依赖求解和游戏启动核心。macOS 使用 SwiftUI；Windows 和 Linux 分别使用适合各自平台的原生 UI 库，具体库尚未选定。Desktop 与 Core 分离的首要目的，是让三个原生客户端复用同一套业务能力，而不复制业务实现。CLI 也可复用这些能力。

本规范采用六种职责：Shell、Contract、Application、Domain、Ports、Adapters；Host 是部署入口与组合根，不强行作为第七层。职责不等于程序集数量。

约束用语：

- **必须／不得**：迁移范围内需要遵守的边界。
- **建议**：默认做法，有具体理由时可选其他实现。
- **后续阶段**：尚未实现的目标，不得据此宣称现有功能已具备。

当前0.40实现仍是 Apple Silicon Mac 上的 Avalonia + 独立 Host。Avalonia 是渐进迁移期间的可用入口和功能对照，不是三平台最终统一 UI；SwiftUI 是 Mac 端明确的目标，不再表述为可选设想。Windows/Linux 原生界面和各平台 Adapter 必须分别实施及验收，不能从 Mac 运行证据推导三平台可用。

当前实现追踪：[0.40 Core 职责与页面生命周期验收](../0.40-Core职责与页面生命周期验收.md)。具体验收状态以该报告为准，规范本身不作为运行证据。

### 1.1 三平台 Shell 与共享核心

| 平台 | 目标 Shell | 当前范围 |
|---|---|---|
| macOS | SwiftUI | 当前包仍为 Avalonia；SwiftUI 完整客户端待迁移和验收 |
| Windows | Windows 原生 UI 库，具体选型待定 | 不将上游 Windows PCL2 视作已接入本项目 Host 的客户端 |
| Linux | Linux 桌面原生 UI 库，具体选型待定 | 桌面环境、工具包及支持范围需后续决策和实测 |

这里的 Desktop 是展示职责，不等同于现有 `Pcl.Desktop` Avalonia 项目。三个客户端可以使用不同语言、窗口导航和系统交互；业务规则、任务真相和持久化仍由共享应用核心及各平台 Host/Adapters 负责。共享核心指同一套实现按目标平台构建部署，不是三个系统共用同一个可执行文件。

跨语言客户端共享的是版本化的请求、响应、错误、事件和生命周期语义，不能要求 SwiftUI 直接引用 `Pcl.Contract.dll` 或 `Pcl.Client.dll`。现有 .NET Client 是一种协议实现；Swift 等客户端需实现对应的类型映射、请求关联、取消、订阅、会话恢复和资源释放。协议文档与契约一致性测试应覆盖这些语义，不能在新客户端重写安装、登录或依赖求解。原生窗口/授权交互可由 Shell 承担，凭据存储与刷新仍由 Host 通过 Ports/Adapters 管理。

## 2. 编译依赖与运行时调用

### 2.1 编译依赖

下列箭头表示“左侧引用右侧”，不表示执行顺序：

```text
Shell             -> Contract + Client
Client            -> Contract
Host              -> Application + Adapters + Contract
Application       -> Domain + Ports + Contract
Adapters          -> Ports + Domain 的必要数据类型
Ports             -> Domain 的必要值类型 + 标准库
Domain            -> 标准库
Contract          -> 标准库
```

上表描述 .NET 组件拆分后的依赖目标；Swift 等非 .NET Shell 对 Contract 的依赖是协议语义依赖，不是 CLR 程序集引用。阶段一同进程且没有 Client 时，展示代码直接调用 **Contract 中定义的应用接口**，不需要经过传输层；`VersionInstallService` 在 Application 中实现该接口，由 Bootstrap 构造后以接口类型注入 Shell。以下两种路径的区别是传输方式，不是允许 Shell 组装实现：

| 阶段 | Shell 调用路径 | Application 实现的组装位置 |
|---|---|---|
| 一：同进程、无 Client | Shell -> Contract 应用接口 -> 注入的实现 | 当前可执行项目的 `Bootstrap/Composition.cs` |
| 三：进程外 | Shell -> Client -> RPC -> Host 中的应用接口实现 | 独立 Host 的组合根 |

因此“同进程调用应用入口”不等于“展示代码引用 Application 实现类型”。阶段一无需新增 `Shell -> Application` 实现依赖例外；组合根的实现引用例外仍限于规则 6。Contracts 与 Application 暂处同一 Core 程序集时，也按命名空间／符号约束此边界。

补充规则：

1. Domain、Ports、Contract 不得依赖 Application、Adapters、Shell 或 Host。
2. Domain 保持纯规则，**不得引用 Ports，包括 Ports 的接口或值类型**；不通过服务定位器、静态全局对象或反射绕过依赖边界。本项目的外部能力接口由 Application 消费，集中放在 Ports。
3. Adapters 不得依赖 Shell、Application 的编排实现或 Host。Adapter 实现 Ports；核心不引用其实现类型。
4. Application 负责 Contract 与 Domain 类型的映射。Domain 不为适配界面或 RPC 字段而改变业务语义。
5. Client 是可选客户端代码，负责传输、请求关联和事件分发，不承载业务流程。
6. 当前 Avalonia 可在可执行项目内保留 `Bootstrap/Composition.cs`。该目录是组合根例外，不视作 Shell 展示代码。程序集拆分后，独立 Host 无须反向依赖 Shell。
7. 目录阶段采用命名空间、迁移清单和用例追踪约束；程序集阶段再增加项目引用及传递依赖约束。目录分层本身不提供编译隔离。

本规范没有 `Domain -> Ports` 的引用边，因此 `Ports -> Domain` 不构成环。不得从讨论稿中补回前一条边。需要外部数据时，由 Application 经 Port 获取，再作为显式输入交给 Domain。

类型按职责归属，不统一装进 Shared：

| 类型示例 | 拟归属 | 约束 |
|---|---|---|
| `TargetPlatform`、版本约束等业务值类型 | Domain | 只含显式数据／纯规则，不在属性或静态成员里探测宿主 |
| `FileSystemCaps`、内部 `ProcessSpec` | Ports | 描述技术能力／执行输入，Domain 不依赖它们 |
| `OperationId`、请求及公开事件结构 | Contract | 不成为 Domain 的依赖；不将内部进程参数投射为公开 DTO |

现有 `TargetPlatform.Current` 在迁移时需要把宿主探测移到 Adapter／组合根，不能原样搬进纯 Domain。内部需要操作标识时可使用应用层标识或显式映射，不以复用字段为理由引入反向引用。

当前不建立 `Pcl.Kernel`。只有出现确实独立于 Domain、Ports、Contract，且被多个边界共同需要的稳定值类型时，才通过决策记录引入叶子程序集；不得用 Kernel 或 Shared 收容所有暂时不知归属的类型。

### 2.2 运行时调用

```text
UI 输入 -> Client / 应用接口 -> Application
                              |-> Domain 计算规则与计划
                              |-> Ports -> Adapter 执行外部操作
结果 / 状态 / 进度 <- Contract 映射 <- Application
```

Contract 是数据和接口约定，不是必经的运行时服务。调用 Adapter 与 Adapter 在编译期依赖 Ports 可以同时成立。

## 3. 六种职责

| 职责 | 必须负责 | 不得负责 |
|---|---|---|
| Shell | 控件、输入、导航、选中状态、展示缓存、订阅、错误码本地化 | 唯一的依赖求解、Java 匹配规则、安装提交或后台任务真相 |
| Contract | 请求、结果、事件、错误、能力及版本约定 | 平台 API、服务组装、业务状态存储 |
| Application | 用例入口、校验与授权协调、计划执行、任务生命周期、锁、错误映射 | 界面控件、直接选择具体平台实现 |
| Domain | 版本约束、依赖求解、兼容判断、安装计划和启动参数规则 | 网络、磁盘、进程、宿主 API、运行时平台探测 |
| Ports | 外部能力及其行为约定 | 具体平台实现、UI 控件抽象 |
| Adapters | 网络、持久化、凭据、进程、文件系统及系统集成的技术实现 | 决定用户能否安装某加载器等产品规则 |

Domain 可使用标准集合、JSON 数据处理及跨平台密码学等纯计算。输入必须显式传入；时间、随机数和宿主环境等影响结果的值，不得在规则内部隐式读取。

“只被 UI 调用”不是违规；“业务规则只存在于 UI”才是问题。Shell 可缓存列表和进度以便展示，但必须能从应用服务重新取得权威状态。

## 4. Shell 的边界与取消

Shell 可以：

- 为搜索防抖、关窗、停止订阅和视图异步加载持有 `CancellationTokenSource`。
- 校验输入格式以提供即时反馈；Application 仍必须进行权威校验。
- 将稳定错误码及结构化参数转换为文案，提供重试或取消按钮。
- 在同进程阶段调用应用接口；在 RPC 阶段使用 Client。
- 为窗口装饰与系统集成探测宿主平台，例如红绿灯位置、全屏行为、打开网址或文件夹；不得用该探测决定版本、加载器、Java 或 natives 等业务分支。窗口行为与游戏目标平台不得混用。

Shell 不得：

- 根据异常文案决定业务分支，或把 `catch` 后的盲目重试当作恢复机制。
- 在业务事件处理器中创建安装器、下载器、凭据存储等核心实现。
- 通过关闭窗口的取消令牌隐式终止已被接受的后台安装。
- 计算唯一的内存上限、依赖版本约束、Java 选择和 natives 选择规则。

服务、视图模型和控件的构造本身不违规；限制针对隐藏组装业务依赖。纯界面导航、排序、折叠不必变成核心命令。

## 5. 应用服务入口

### 5.1 入口规则

每个迁移用例有一个明确的 Application 入口。入口通过构造注入取得依赖，接收 Contract 请求，返回 Contract 结果或操作受理结果。

Application 负责：

1. 验证请求、配置与能力，区分下载权限和启动认证策略。
2. 调用 Domain 得出计划，协调 Ports 执行。
3. 串行化相互冲突的修改操作，持有后台取消源。
4. 将内部异常映射为稳定错误，不将原始异常作为协议返回值。
5. 确定新建对象、共享对象和外部进程的所有权。

Application 不得成为单个万能服务。版本安装、账户管理、游戏启动等按用例组织；公共机制单独实现。

### 5.2 长任务的受理边界

“立即返回 operationId”指在有限的本地校验、持久化受理和入队后返回，不承诺零延迟。

不得在受理之前完成远程元数据读取、依赖求解、下载或解压。这些阶段也可能耗时或失败，必须属于可查询、可取消的操作。

不得以无人持有的 `_ = Task.Run(...)` 实现可靠后台任务。应用级 runner 必须持有任务、观察异常、写终态，并参与关闭流程。I/O 任务使用异步 API，只有需要时才将 CPU 工作交给有界工作池。

## 6. 契约与数据模型

### 6.1 DTO

跨 Shell／Host 边界的 DTO 必须：

- 只有可序列化数据，不包含 `Task`、流、句柄、委托、UI 类型或 `Process`。
- 明确必填、可选、单位、范围、枚举未知值和空值语义。
- 使用稳定 ID 关联账户、实例、操作和游戏进程。
- 将进度计数和阶段名分开；未知总量用显式空值，不用伪造百分比。
- 对可展示路径明确其属于宿主还是目标。路径不替代实例身份。

内部 Port 可以返回强类型内部对象或流，并明确释放责任；“只能纯 DTO”主要约束跨进程与 Shell 边界，不能机械套用到流式下载或内部资源句柄。

### 6.2 版本与兼容

契约版本独立于应用版本。新增字段只有在旧客户端允许忽略、具有兼容默认语义且未改变必填要求时，才属于兼容变更。

新增必填字段、改变现有含义或单位、删除字段、改变默认行为均须评估兼容。新增枚举值也可能破坏客户端，必须约定未知值处理或提升版本。

不得要求“接口永远只加不改”。已发布契约通过版本和弃用周期演进；未发布内部接口可以随迁移修正。

### 6.3 错误

错误包含稳定 `code`、可选安全说明、结构化 `detail` 和重试建议。Shell 不解析说明文字。

至少区分：无效参数、策略不允许、能力不支持、依赖冲突、实例忙、认证过期、权限拒绝、网络故障、磁盘不足、校验失败、取消和内部错误。

`IOException` 等语言异常不能单独决定错误语义；错误映射需结合操作阶段和具体原因。超时不自动等于可安全重试，重试建议应区分：

- `none`：当前请求不应自动重试。
- `sameOperation`：用原幂等键重查／重试受理，避免重复副作用。
- `newAttempt`：终态后可由用户发起新一次操作。

原始异常、内部堆栈、令牌和敏感命令行不进入 DTO 或公开日志。

## 7. 命令与进程外协议

### 7.1 协议选择

第一阶段使用同进程应用接口，不为接线提前部署 Host 子进程。

进入进程外阶段后，默认采用 **PCL 自定义 RPC v1**：借用 JSON-RPC 结构，使用 UTF-8 NDJSON 传输；不声明兼容 JSON-RPC 2.0。未来如使用标准 JSON-RPC，必须明确实现和兼容范围。

传输不会进入 Domain。进程内客户端和进程外客户端保持相同业务含义；原生 dylib / C ABI 桥接是后续独立决策，不承诺直接暴露 C# 对象。

### 7.2 消息示例

命令按“名词.动词”命名。示例中的对象必须序列化为单行发送：

```json
{"protocolVersion":1,"id":"req-7","method":"version.install","params":{"idempotencyKey":"attempt-9b31","gameVersion":"1.21.1","loader":"fabric","targetPlatform":{"os":"osx","architecture":"aarch64"}}}
```

受理结果：

```json
{"id":"req-7","result":{"operationId":"op-42","state":"queued"}}
```

事件：

```json
{"event":"operation.progress","operationId":"op-42","seq":12,"data":{"stage":"download","completedBytes":1240,"totalBytes":9000}}
```

失败结果使用 `error`，与 `result` 二选一。v2 中的 `cmd/args/ok/data` 为讨论示例，本规范统一为 `method/params/result/error`，避免实现两套信封。

### 7.3 消息与连接规则

- 握手协商协议范围、Host 实例 ID 和功能能力；不兼容时给出明确错误。
- 每个请求 ID 在客户端会话内唯一；不会在仍可能收到迟到响应时重用。
- 响应可以乱序，但必须准确匹配请求；未知／过期请求响应不得派给新请求。
- stdout 只输出协议，stderr 输出脱敏诊断；底层库的普通日志不得污染协议流。
- 初始帧上限为 1 MiB，超限明确拒绝。大日志、图片和文件使用受控资源引用与分块／分页能力。
- 单写队列确保消息不交错，解析不得依赖一次读取恰好等于一条消息。
- 父进程直接启动私有 stdio Host；若以后支持 socket，另行定义身份验证、权限和端点访问控制，不能默认开放网络端口。
- RPC 只提供明确命令，不提供任意命令执行、任意 Java 参数注入或无约束文件读取。

### 7.4 事件、背压与快照

进度可合并为每个操作的最新值，默认最多每 50 ms 发一次；时间和队列上限是可配置运行参数，不是业务规则。

受理响应、终态和关键状态不得因丢旧队列策略丢失。普通日志可以有界截断，但必须报告截断。可靠事件的慢消费者策略为有界等待后断开并要求重新同步，不能无限占用内存或阻塞安装提交。

持久化操作状态是事实来源；连接断开时不保证接收端收到终态通知。接收端必须能够通过查询恢复结果，不能把“未收到事件”解释为操作尚未完成。

每个操作的事件 `seq` 单调递增；允许因合并产生间隔，接收端不得据此认定任务失败。状态快照返回对应水位。订阅必须支持从水位衔接，或使用“先缓冲订阅、再取快照”的一致机制，消除“查完状态再订阅”之间的丢事件窗口。

## 8. 操作生命周期、幂等与并发

### 8.1 标识与状态

| 标识 | 含义 |
|---|---|
| requestId | 一次通信请求 |
| idempotencyKey | 同一次用户意图的受理去重键 |
| operationId | 一个后台操作及其状态、日志、结果 |
| instanceId | 一个游戏实例 |
| gameProcessId | Host 管理的游戏运行身份；PID 仅为辅助信息 |

操作状态：

```text
queued -> running -> succeeded / failed
queued / running -> cancelling -> cancelled / succeeded / failed
Host 异常退出时的非终态 -> interrupted
```

`stage` 单独记录规划、下载、校验、解压、提交等阶段。受理不等于安装成功；一次 `game.launch` 操作成功只表示游戏进程已创建，其后退出由独立游戏进程状态跟踪。

### 8.2 取消与提交

请求等待令牌只控制调用方等待；已受理任务使用应用服务持有的令牌。用户通过 `operation.cancel` 请求取消。

取消被接受不等于已停止。提交前应尽快停止并清理不安全半成品；进入不可安全中断的提交区间后，必须完成提交或恢复，再给出真实终态。不得安装已成功却仅因收到取消请求而报告 `cancelled`。

在阶段三独立 Host 模型下，重连、关闭视图和 UI 崩溃不隐式取消后台任务。明确的应用退出请求按 §8.5 处理。阶段一同进程的取消及退出兼容范围见 §14，不能声称 UI 进程退出后安装仍会存活。

### 8.3 幂等键

所有可能产生副作用的受理命令必须明确重复请求策略，包括安装、复制、登录和游戏启动：

- 同键、同规范化参数：返回同一 operationId 或已保存结果，不重复执行。
- 同键、不同参数：返回 `IDEMPOTENCY_CONFLICT`。
- 用户主动再次登录或启动第二个游戏：使用新键，再由产品并发策略决定是否允许。
- 已取消／失败操作的新尝试：使用新键，可携带 `resumeOfOperationId`。不得悄悄把旧终态改回运行。

键必须按数据目录和命令类型划定作用域；规范化输入包含目标平台、实例和影响结果的选项。不得用固定的 `install-1.21.1-fabric` 代表所有安装尝试。

支持重启去重的阶段，必须先持久化键与操作映射，再响应受理。明确保留期与过期后的语义；受理去重本身不保证任意外部副作用“恰好一次”。

### 8.4 并发

同一实例的修改操作默认互斥，安装、修复、删除、续做需共享一致的锁规则；资源下载可以按有界并发进行。

同一数据目录只有一个管理 Host 拥有写入权。可并行的操作也必须保护共享缓存、索引和凭据刷新，不能只依靠 UI 禁用按钮。

跨进程锁的具体实现列为 §17 的 DEC-003，进入阶段三前必须完成。阶段一继续由现有入口持有 `.launcher.lock` 的独占句柄，组合根接线不得提前释放它，也不得让第二个窗口或工厂获取另一套写入权。锁文件存在与否不代表锁是否被持有。

### 8.5 退出路径与关闭责任

关闭一个视图、隐藏启动器和退出应用是不同事件。Shell 请求一种明确的关闭意图，由生命周期协调者决定是否退出 Host；不能只靠 `Window.Closed` 同时承担取消、保存和全部资源释放。

| 路径 | 任务处置 | 状态与恢复 |
|---|---|---|
| 用户明确退出应用／Host | 停止受理新操作，向可取消任务发出取消请求，异步有界等待安全停止或提交收尾，再释放资源 | 记录实际完成的终态。预算用尽但未能确认停止时记录关闭原因及最后安全阶段；下一 Host 在确认旧写入者已退出并取得独占权后转为 `interrupted` |
| 系统关机、注销或系统要求立即终止 | 停止受理，尽力保存已知快照与可安全落盘的 checkpoint／提交记录；只使用系统允许的剩余预算，不进入普通退出的任务等待流程 | 不承诺系统一定发送通知或允许落盘；未保存成功的状态按异常中断恢复，不能标为正常完成 |
| 崩溃、强制结束或断电 | 不依赖退出回调、`finally` 或临时补写 receipt；运行期间已完成阶段的记录才可用于恢复 | 下一 Host 按 §9.2 处理非终态、校验 receipt 与提交记录，不推断为已取消或已完成 |

执行约定：

1. 用户退出的等待预算必须有限、可测、可配置；阶段一给现有托管安装调用接入此边界，实际预算随实现记录，不在文档中伪造已验证的安全时长。等待不得使用 UI 线程上的同步 `Wait`／`Result`。
2. 只在安全边界写 checkpoint，不与仍在进行的文件提交并发改写同一记录。能保证的是保留可恢复证据，不能保证所有中断场景都完成回滚。
3. 超过预算不得先释放正在被任务使用的 HttpClient／存储对象，再让任务继续执行。在同进程模型中，进入最终进程退出收尾；在独立 Host 模型中，明确选择继续后台运行或退出中断。不能把界面关闭冒充 Host 已退出。
4. 仍在持有写锁且执行的任务，不得提前对外标成 `interrupted`。可提前持久化关闭意图；确定失去执行者后的中断认定由下一独占 Host 完成。已得到真实终态的任务保留原终态。
5. 数据目录独占权必须保持至写入者停止或进程退出。不能先释放 lease 再做最后一次状态／receipt 写入。
6. 已运行游戏与安装任务分开处理。遵守现有保留游戏、隐藏启动器和独立启动策略；`Dispose` 不无条件终止游戏。普通关闭窗口当前可能只隐藏窗口，这种行为不是“用户明确退出应用”。
7. 系统终止通知不等于可用的保存保证。receipt 和提交日志必须在运行时按必要边界持久化；系统终止路径也不得强行把尚未验证的中间状态记录为安全 checkpoint。

阶段一的协调者可以位于当前可执行项目的 Bootstrap 内，持有已迁移的安装 Task 和取消源，不要求先建立完整 operation runner。旧窗口的重复 `Closed` 释放需随接线移交所有权，避免两处关闭同一共享服务。

## 9. 会话恢复与任务续做

### 9.1 UI 连接恢复

同一个 Host 仍存活时，UI 重连通过操作快照、水位和事件恢复展示，不重新发起相同安装。短暂断连不需要重新校验所有下载文件。

### 9.2 Host 重启后的状态恢复

Host 内存已丢失，必须读取持久化操作记录。只有数据目录的管理 Host 可以执行中断标记与恢复协调，不能由每个新建窗口执行。

启动时将无法确认完成的非终态转换为 `interrupted`，再按 receipt 与提交日志确认后续动作。不能从内存注册表声称恢复了准确进度；也不能把 `interrupted` 伪装成仍在运行。

### 9.3 安装续做

receipt / 提交日志至少记录：格式版本、原操作与实例身份、游戏／加载器精确版本、目标平台、元数据身份与哈希、计划摘要、文件清单、提交阶段和必要恢复信息。

- 任务记录和 receipt 的业务语义由 Application／Domain 定义，持久化实现放 Adapter。
- 新记录采用版本化独立操作记录；首次迁移继续读取已有 `install-operations.json`，不得直接丢弃历史状态。
- receipts、临时文件和目标目录都视为不可信输入，恢复前验证格式、路径和身份。
- 已下载内容按可信元数据重新校验；临时文件存在不代表可复用。
- 同一目标版本标识下的元数据可能变化，不能仅凭版本名称续做旧计划。
- 外部安装器和不可重放步骤必须有恢复策略；不支持可靠续做时明确告知需要重做该阶段。
- 新尝试通过 `resumeOfOperationId` 关联旧记录，保留原失败或取消结果。

仅有任务历史 JSON 或重新调用一次安装器，不等于具备可靠断点续做。

## 10. Ports 与平台实现

### 10.1 接口设计原则

接口由使用方需要的能力定义，一个接口对应一个清晰的变化理由。数量只作复盘信号；`>12`、增长过快、重复接口或不相关能力捆绑时开展设计复盘，不作自动停工门禁。

不一次性建立全部接口。新增 Port 必须说明真实使用方、隔离的副作用或平台差异、资源所有权和失败语义。

| 候选边界 | 约定 |
|---|---|
| `IAccountSecrets` | 沿用已有名称与语义；同步原生调用由 Adapter／应用调度避免阻塞 UI |
| `IShellCommandRunner` | 短命令异步等结果；参数列表、输出限制、超时及取消后的清理明确 |
| `IGameProcessHost` | 创建长进程、逻辑身份、退出观察、停止与日志；支持明确的脱离策略 |
| 宿主平台提供器 | 提供当前启动器的 OS、架构及能力，不替代目标平台值对象 |
| 路径与文件系统能力 | 按路径／卷查询；未知能力显式表示；保留原始大小写 |
| Java 运行时提供器 | 接受显式目标和候选信息；技术获取实现与业务匹配规则分开 |
| 系统集成 | 打开经验证的网址、显示文件、通知、应用徽标；不回流 UI 控件 |
| 网络／下载、持久化、时钟 | 按实际用例逐步抽取，不为凑齐接口预建空实现 |

### 10.2 进程

进程输入使用可执行文件路径、参数列表、工作目录和受控环境。默认不经过 shell 拼接字符串。

长进程身份不得只依赖 PID，避免 PID 重用误杀其他进程。Adapter 内部保留原生句柄或创建身份校验，外部使用逻辑 ID。

等待退出的取消与终止进程必须分开；日志需要有界、可截断和脱敏。Adapter 必须回收短命令的输出与退出状态，防止输出管道阻塞。

“游戏可脱离启动器”需要显式的进程、日志与释放策略。Host 退出后是否继续游戏由已有产品设置决定；不得在统一 `Dispose` 时无条件杀死所有游戏。Host 重启后无法可靠重新接管的进程必须明确标注能力限制。

### 10.3 路径、卷和事务

路径绝对化不得统一转小写。路径比较、大小写敏感性、Unix 权限和符号链接能力按目标卷／目录判定；不能由 OS 名称推断所有卷的行为。

字符串前缀不是可靠的目录包含关系。写入／解压／恢复需防止 `..`、链接重定向和操作期间路径替换等越界，具体防护由文件系统及归档 Adapter 实现。

原子文件替换只在支持的文件系统和操作条件下承诺；默认在目标目录内 staging，跨卷移动不得冒充原子提交。多个文件／目录的安装事务需要日志与恢复流程，不能由单个 `ReplaceAtomicAsync` 名称代替。

不可中断提交区间应以秒级为设计目标，并尽量缩短。下载、解压、递归复制、全量校验及跨卷搬移必须在可取消的准备阶段完成；提交阶段只执行必要的日志持久化、已准备文件的替换和提交标识发布。不得把整目录递归搬运包成一次长时间不可取消的事务。

实施时必须满足：

- 优先采用目标卷 staging、明确的提交前日志和可恢复的逐文件替换，或经验证的目录／版本指针切换。单次原子目录重命名与递归复制不是同一种操作，不笼统禁止前者。
- “逐文件原子替换 + 最后写 manifest”不自动构成多文件原子事务。需要明确 manifest 的提交语义、途中失败的回滚／重做规则，并阻止读者或游戏在不允许的半提交状态下使用该实例。
- 不能安全并发修改正在运行游戏的实例时，必须通过实例状态及锁规则拒绝或推迟修改，而不只拦截新一次启动。
- 实现记录正常及慢存储场景下的提交耗时，并据此制定退出等待预算。秒级目标或例如五秒的等待预算，不是对文件系统调用完成时间的硬保证；超出预算仍按 §8.5 和提交日志处理。

### 10.4 宿主平台与目标平台

| 场景 | 依据 |
|---|---|
| 使用哪种凭据存储、如何启动进程、系统集成 | 宿主平台与能力 |
| 下载哪个 natives、哪种 Java 包、生成何种启动参数 | 显式目标平台与版本规则 |
| 目标 Java／游戏能否在本机执行 | 宿主与目标的能力匹配 |

沿用并逐步拆清现有 `TargetPlatform`；平台取值可以作为普通数据进入 Domain，Domain 不自行探测宿主。Mac 上可规划其他平台文件，不等于允许在 Mac 执行 Windows 安装器或程序。

Adapter 可以根据 OS 版本、原生 API 支持和归档格式作技术分支；游戏兼容性、依赖约束和账户策略仍归核心规则。

## 11. 组合根、第三方依赖与资源所有权

组合根采用静态工厂即可，不要求 DI 容器：

- 每个应用／Host 生命周期、每个数据目录的管理作用域创建一套服务。
- 只负责组装、选择实现和建立释放责任，不包含安装或登录规则。
- 返回有明确接口和生命周期的服务持有对象；不得建立 `Composition.Instance` 或全局服务定位器。
- 业务对象通过构造参数取得依赖；不得在运行期间重新调用工厂获取隐式新服务。
- 关闭时先停止受理、退订与请求后台停止，再等待安全落盘，最后释放网络、存储和其他资源。保留游戏的分支需独立处理。

MeloongCore、PCLCS、Pcl.Legacy 当前是 Core 的直接依赖。迁移时逐步通过现有核心门面／Adapter 包装，最终纯 Domain 不引用其平台或全局状态实现。

既有全局初始化集中在入口／组合根启动过程，明确执行次数和线程要求。不能在每次安装或测试中重复初始化以掩盖依赖。

不得改变 macOS 钥匙串的现有命名空间、账户 ID 或数据目录作用域而不提供迁移办法。`IAccountSecrets` 移动位置或改变命名空间时兼容现有调用，避免仅为改名破坏凭据恢复。

## 12. 安全与产品行为边界

- 保持下载、安装与账号认证的现有产品分离；架构重构不顺带改变离线登录或微软登录策略。
- 不新增赞助、支付或主题解锁流程；保留上游必要署名与许可证。
- 公共 OAuth client ID 可作为应用配置；client secret、refresh token、access token 不进入公开配置、receipt、日志或普通 RPC DTO。
- Shell 通过 accountId 请求登录或启动，由 Host 内部管理敏感凭据。需要给用户展示的短时授权提示另设最小数据契约。
- 进程参数可能包含敏感值，内部 `ProcessSpec` 与可记录／可公开的命令摘要必须分开；不因“统一 DTO”将完整参数暴露给 UI。
- 架构迁移不得放松文件哈希、归档路径、加载器依赖、Java 匹配或原生库适配的既有保护。

## 14. 迁移阶段与完成条件

### 阶段一：应用入口与最小组合根

范围：保留 Avalonia、现有 Core 和构建方式；先目录分层，不新增 RPC 子进程或全量 Port。

建议初始目录：

```text
src/Pcl.Core/
  Contracts/Installation/       # 请求、进度、结果、应用接口
  Application/Installation/     # VersionInstallService
src/Pcl.Desktop/
  Bootstrap/                   # Composition 与服务生命周期
```

这是过渡布局：Contracts 暂与 Core 同程序集，依赖可见性还不能靠项目引用强制保证。后续才考虑独立 `Pcl.Contract`、`Pcl.Application`、`Pcl.Domain`、`Pcl.Ports`、Adapters、Client 和 Host 项目。

入口建议先采用“等待安装完成”的 Task 接口，忠实转发现有进度和取消；此时不伪装成已经具备 operationId、可脱离后台任务和 RPC 恢复。

完成条件：

1. `Composition.Create` 在启动入口创建一次本作用域服务，有明确释放责任。
2. `VersionInstallService` 构造注入现有门面，内部真实调用 `InstallOperations -> VersionInstaller`，不另造第二套版本匹配和安装计划。
3. 一个现有 Avalonia 新安装入口确实经应用服务执行，Request 明确版本、加载器及当前支持的目标；拒绝不支持的字段，不静默丢弃。
4. 用 DTO 映射现有进度／结果，不把 `MinecraftService`、`GameProfile` 的实现依赖或 UI 类型泄漏为公开调用约定。
5. 修复路径与新安装路径维持原有区别；没有因为套门面漏掉现有安装任务记录、错误和取消行为。
6. 窗口代码不再为该迁移用例组装安装服务；其余旧入口列入迁移清单，不宣布整体 Shell 已解耦。
7. 编译通过；根据获准范围实际调用迁移入口，记录行为证据与未执行项。
8. 明确已迁移安装 Task 的退出协调者、取消源、等待预算和释放责任；实际触发明确的应用退出意图后，按 §8.5 验证取消、提交收尾与释放顺序。通过结构化生命周期日志或计数替身证明同一共享服务的拥有者只释放一次，且任务仍在使用依赖时不会被窗口 `Closed` 提前释放；重复关闭／释放入口不得导致重复清理或新异常。保留现有游戏窗口隐藏／独立游戏策略：仅隐藏主窗口时不误判为应用退出。验证范围按当轮授权执行，未执行时明确记录，不能仅写明责任人就标为通过。
9. 将本阶段的契约版本、调用点与预计二次修改范围记入下表；不以 `InstallHandle` 空壳或预留字段声称阶段三语义已经实现。

第一阶段的请求取消令牌可以继续控制当前安装调用。这是明确的兼容过渡，不满足后续“已受理后台任务独立存活”语义；进入阶段三时必须更换契约版本／入口语义，不能静默改变原调用。

#### 预计二次修改的调用点

第一阶段选择等待安装完成的 Task，接受后续向操作受理模型迁移时的二次改动。该改动是已记录的取舍，不作为遗漏补丁偷偷实施。

| 位置 | 阶段一范围 | 阶段三预计变化 |
|---|---|---|
| `MainWindow.axaml.cs` 新安装分支及其 `RunAsync` 调用 | 优先迁移候选：等待应用服务结果，转发当前进度与取消 | 接收 `operationId`，按快照／事件更新；请求取消与断开等待分离 |
| `VersionManager.cs` 版本安装分支 | 同类入口按实际迁移范围复用服务；未迁移时保留登记 | 使用同一受理接口与操作事件，不复制任务管理逻辑 |
| `TaskCenterWindow.cs` 继续安装与读取任务历史 | 第一阶段可保持旧路径，明确登记；不假称已接统一应用服务 | 查询操作与持久化历史，续做创建关联新操作，取消按 `operationId` |
| 安装 Request／Progress／Result DTO 与应用接口 | 表达当前单次调用的完成、异常和取消 | 新增明确版本／入口的受理、快照、事件和续做契约；保留必要兼容适配 |
| `App.axaml.cs`、`MainWindow` 关闭回调与 `Bootstrap/Composition.cs` | 当前同进程作用域的创建、安装 Task 追踪、退出及资源释放 | 协调 Client、Host 生命周期、后台任务与连接退出策略；写锁所有权转交 Host |

实现阶段一时据实际改动更新表中“已迁移／未迁移”，不要求本轮把所有入口一起迁完。修复、整合包、组件安装等其他路径单独登记。

### 阶段二：凭据与长短进程边界

迁移现有凭据接口和具体存储实现，拆短命令与游戏长进程。先建立实际 Adapter，再用小范围调用替换原生操作；不为完成目录图重写所有核心服务。

完成条件：调用方依赖能力约定，真实 Adapter 能承担当前行为；凭据作用域和游戏退出／保留语义明确，相关接口可用替身调用。

### 阶段三：操作、恢复与进程外契约

按顺序建立 runner、操作存储、幂等受理、取消、快照／事件衔接、receipt 与续做，再接入 stdio Host。

进入独立 Host 之前必须完成 §17 中 DEC-003、DEC-004、DEC-005 的决策及对应实施；不能仅凭 stdio 能收发 JSON 宣称跨进程架构完成。

端到端链路：`version.install -> operation.cancel -> 会话状态恢复 -> 新尝试续做 -> game.launch`。

恢复实验分别覆盖 UI 断连、Host 重启和提交中断；不以一次普通安装成功代表恢复通过。未支持的安装器续做能力明确暴露。

### 阶段四：SwiftUI 最小链路

SwiftUI 通过 Swift 客户端适配接入现有 Host 契约，先跑通安装 → 取消 → 会话恢复 → 任务续做 → 启动，再扩大功能覆盖。验证请求/响应类型映射、错误码、事件水位、重连、退出及单一释放；不直接依赖 .NET Client 程序集或复制业务规则。

迁移期间保留 Avalonia 作为可用入口和同用例对照。SwiftUI 的账户、皮肤、实例、资源与游戏生命周期取得对应证据后，再决定替换默认入口；不得因换 UI 丢失现有微软/离线登录、皮肤及游戏独立运行行为。

### 阶段五：拆程序集与扩平台

依据实际边界和迁移成本继续整理程序集；已经完成的拆分不重复实施。使用项目引用、传递依赖与符号约束验证边界。分别选定 Windows 和 Linux 原生 UI 库，复用同一 Host 协议及业务实现，补齐各平台凭据、文件系统、进程和系统集成 Adapter。逐平台验证安装/取消/恢复/启动、登录/皮肤及关窗后游戏生命周期，不能把共用代码当作平台实际运行证据。没有固定“三周”或“一小时完成全部收口”的承诺。

状态仅使用有证据的描述：拟定、已接线、已编译、替身运行、平台实际运行、未执行、有已知限制。文档示例不算实现，编译通过不算实际安装成功。

### 15.1 过渡期可执行守卫

Desktop 的 `EnforceArchitecture` 构建目标执行 `scripts/ArchitectureGuard`：检查 Core/Client/Desktop/Host 的实际项目运行时引用集合，并扫描已编译 Desktop 方法体与字段符号；Bootstrap 之外不得引用或构造 `Pcl.Core.Application.*`、`Pcl.Core.Adapters.*` 的实现。别名、全限定名、目标类型 `new`、异步状态机仍按解析后的符号判断。违规使构建失败；`ReferenceOutputAssembly=false` 的 Host/守卫构建依赖不当作运行时引用。

以下为0.25过渡期记录，不是允许恢复旧依赖的现行例外；0.32已移除 Desktop → Core/Application 及 Bootstrap 业务桥，见[0.32验收](../0.32-架构实现与验收.md)。0.25时已移除 Client → Core，但当时仍保留 Desktop → Core/Application 和 Bootstrap 接线例外，见技术债及构建输出的 `architecture-guard.json`。守卫尚未禁止全部旧 Core 根命名空间 API，也不是业务规则用例追踪的替代品；字符串反射不在静态符号检查的证明范围内。不得将“当前守卫通过”写成“Shell 已无法访问 Core”。

Contract 可在阶段五前单独抽成程序集，不要求一次拆完所有层。但要分别验收：

1. Contract 只保留 DTO/应用接口，无 Core、传输、文件或进程实现依赖；Client 迁出对 Core 分帧/诊断工具的依赖后，项目及传递编译引用才可收紧为 Client → Contract。
2. Desktop 的旧页面和 Bootstrap 仍依赖 Core 时，必须保留并登记该过渡边，不能因抽出了 Contract 就宣称 Desktop 获得编译隔离。移除该边需要迁移剩余页面与公开类型，并复核传递引用。
3. 引用策略变更必须同步修改守卫、正反例测试和用例追踪，不得靠增加泛化白名单让违规通过。

守卫正反例由 `scripts/test-architecture-guard.py` 执行；生产编译通过、故障样本被拒绝分别留证。历史发布包的运行证据与当前源码构建守卫证据分别记录。
