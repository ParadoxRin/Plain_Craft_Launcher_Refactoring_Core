# 后台登录与资源并发

本文描述 `feature/bg-login-integration` 功能分支的设计与验证要求，尚未发布；`v0.42.1` 安装包不因此获得这些行为。版本、更新源、签名策略及数据格式保持不变。

## 所有权

| 层 | 职责 | 不承担的职责 |
|---|---|---|
| Desktop | 跨页面展示登录任务、设备码、取消入口；窗口退出等待回收；页面请求独立管理 | 凭据、事务及权威冲突裁决 |
| Client | 复用登录 RPC；稳定幂等键、重连查询、取消及终态观察；会话关闭兜底回收 | 读取账户文件、核心类型或操作收据 |
| Host / Application | 认证与账户状态、资源冲突、队列与执行期复核、取消和退出 | 通过锁住整个界面保证安全 |
| Core / Ports | 已授权操作的实际执行、平台凭据和文件适配 | 依赖 Desktop 或控制其页面 |

继续使用 `account.login.begin/get/cancel` 与 `account.snapshot`，不增加 DTO 或更改 wire protocol。`LauncherSession.LoginAsync` 的既有签名保持兼容。Host 是登录状态的权威来源，Client 与 Desktop 不另造登录成功状态。

## 页面和任务

页面导航本身不取消登录，也不等待安装或启动准备结束。登录提示与取消入口放在窗口的全局区域；切换页面后仍可找到。用户明确取消或正常退出客户端时才请求终止登录。旧页面请求的结果不能覆盖当前页面。

查询和写任务使用不同的界面入口：浏览不应占据主窗口写操作槽；冲突写请求必须显示受控原因，不能静默丢弃。能进入页面不等于页面上的每个写按钮都可同时执行。

## 并发策略

- OAuth 的网络等待不占有实例写入队列；账户索引和凭据提交仍需保护。
- 并行读取采用明确审查的方法集合。名称带 `read`、`list` 或 `search` 不能自动证明没有缓存写入、准备记录或可变集合副作用。
- 已审查的读取不能排在长写任务之后，使帮助、版本列表和设置浏览因安装而停住。
- 实例、共享库及缓存的实际写入继续使用必要的串行队列；本轮不承诺任意不同实例同时写入。
- 账户变更与登录冲突，游戏运行与修改其依赖文件的操作冲突。受理和实际执行之间必须复核，防止排队期间资源状态改变。
- 未知方法默认采用保守策略，不通过客户端提交“只读”标志绕过保护。

| 操作组合 | 当前处理 |
|---|---|
| 登录等待 + 导航/设置读取 | 允许，登录继续，状态和取消入口跨页保留 |
| 登录等待 + 无关设置保存 | 允许，保存仍走写队列 |
| 登录等待 + 账户增删/凭据变更 | Host 拒绝冲突账户写 |
| 长写任务 + 已审查查询 | 通过独立读 worker 执行，不占写 lane |
| 安装/删除 + ZIP 资源扫描 | 串行，避免打开的文件句柄干扰写事务 |
| 多个实例/共享库写入 | 继续串行，不承诺跨实例全面并行 |
| 游戏启动后 + 排队安装 | 执行前复核，返回受控冲突，不进入安装器 |
| 未知方法 | 保守处理，不推断为并行读取 |

具体方法的可并行分类以 Host/Application 中的策略及测试为准。账户读取返回最近一次完整提交的公开快照，不应观察账户最终提交的中间状态；其他文件查询不保证整个文件系统的事务快照，写操作仍需重新校验输入。缓存元数据查询若会首次创建文件，也必须防止并发提交竞态。

资源 ZIP 扫描（`workspace.browser.list/display`）仍与文件写入串行，避免 Windows 文件句柄阻止安装或删除，但允许在游戏运行和登录等待期间浏览。Java 检测是受控外部进程探测，不能当作纯内存读取。

Client 只在页面任务受理期间持有提交门，随后独立观察每个任务。Desktop 图标请求另设 4 个并发名额：等待名额时不提交 Host；页面更新时取消旧代，退出等待回收。Host 的队列容量限制保持不变。

## 生命周期与兼容范围

取消请求不等于取消完成；Client 等待 Host 终态后才结束任务。取消之后的迟到设备提示不能再次打开浏览器。提示回调异常也应尝试收回已经创建的授权任务。

同一客户端会话短暂断连后使用同一幂等键或 operationId 恢复查询。整个客户端进程重新启动后自动接管尚未结束的 OAuth，不属于当前既有契约的保证范围。无法联系 Host 时不得假造取消成功；Host 仍保持权威冲突保护。

## 分包与验证

Desktop 和 Client 属于客户端更新块，但分别在独立工作树开发；Host/Application/Core 属于 Host 更新块。Contract 的共享变更统一审批，本轮优先不改。数据与内容包、Java 和外部工具不升级。

验收需同时包括：Client 可控协议测试、Application 可重复并发测试、独立 Host 实际设备授权等待期间的读写冲突测试，以及两套真实 Avalonia 布局的可见性与跨页生命周期测试。替身测试、真实设备码请求和真实账户登录分别报告。

此功能分支会修改正式版固定的 Host/Core 业务文件，因此旧版打包基线守卫应报告差异。不得为让功能分支打包通过而篡改 `release.json` 中的版本或固定哈希；发布基线迁移留待另行审查。本轮只构建测试，不发布新版。

## 重复验证入口

使用仓库要求的 .NET SDK，在全新的临时输出目录运行：

```sh
dotnet run --project tests/Pcl.ClientLogin.Tests -c Release -- /absolute/fresh-client-tests
dotnet run --project tests/Pcl.ResourceConcurrency.Tests -c Release -- /absolute/fresh-resource-tests
dotnet run --project tests/Pcl.DesktopQueue.Tests -c Release
python3 scripts/check-module-boundaries.py
```

前三项使用可控协议、资源屏障和图标队列，不需要真实账户或 GUI；Core CI 执行这些回归。真实设备授权等待检查需另行显式运行 `scripts/test-background-login-host.py --help` 中的命令；它不完成账户登录。Desktop 的 `--login-cancel-smoke` 仅能在带 `.login-cancel-test` 标记且目录名以 `login-cancel-data` 结尾的独立数据根执行，分别检查两套布局，必须读取结果 JSON 的 `status`，不能只判断进程退出码。

分包验证应分别构建没有 Desktop/Client 源码的后端闭包和仅消费 Client/Contract NuGet 的客户端工作区，再通过私有管道联测。固定发布基线不匹配时，只能使用测试源码闭包验证；不得将它标为正式组件发布包。
