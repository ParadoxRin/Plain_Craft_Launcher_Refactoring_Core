# 分包交付第一阶段

本文件保留开发过程中的历史验证。当前版本、交付流程及最新结果以 [0.42.1 分包交付](0.42.1-分包交付.md) 为准。

本改动以修复后的 0.42.0 源码 `81016b4` 为当前基线，属于下一版本的开发内容；保留原版本号供验证，不表示下一版本已发布。源码目录与内部业务分层保持现有布局。

## 构建与产物

```bash
bash scripts/build-native.sh
DOTNET=/path/to/dotnet bash scripts/build-components.sh osx-arm64
# 可追加 --base-url https://实际发布站点/版本/平台，生成下载 URL。
```

必须在目标系统/CPU 的 runner 执行，脚本会实际运行候选 Host 的只读探针。当前先验证 Apple Silicon Mac；其他 RID 参数只是构建入口，不代表相应桌面产品已验收。输出目录已存在时拒绝覆盖，避免把旧发布文件混入新产物。可通过 `PCL_COMPONENT_OUTPUT` 选择全新的输出目录。Unix Host 现在需要原生 C11 `cc` 工具链；Mac 辅助程序包含 arm64/x86_64，Linux 必须使用匹配目标平台的 SDK/工具链。

`artifacts/components-<版本>-<RID>/` 内有独立 `client/`、`host/` 部署目录、探针及 `packages/`：

| 文件 | 内容与用途 |
|---|---|
| `*-client.zip` | 完整客户端部署目录，含 Client、Contract、运行时、资源和许可；不含核心 DLL 或 `host/` |
| `*-host.zip` | 完整 Host 部署目录，包含内部程序集、配套 Contract、运行时、原生依赖和许可 |
| `*-full.zip` | 客户端目录加 `host/`；用于部署组合验证，不是可双击的 Mac `.app` 安装包 |
| `release-manifest.json` | 格式版本、频道、版本、平台、大小、SHA256、可选 HTTPS 地址、Host 构建身份、协议、能力与客户端兼容要求 |

客户端的 `BundleHost` 发布属性默认 `true`；分包脚本使用 `-p:BundleHost=false` 跳过发布目录中的 Host 复制。Host 仍为 Desktop 的构建验证依赖，架构守卫会检查两侧程序集；这一阶段拆分交付，不承诺客户端构建完全不编译核心。

现有 `build-handoff.sh` / `build-release.sh` 继续生成含可用 Host 的完整 `.app` 与 ZIP，保留首次安装路径。新增分包 ZIP 是部署资产，不直接替换或写入用户已签名的 `.app`。纯客户端包单独解压后尚不能首次启动业务；部署者须提供兼容 Host。组合部署时将 Host 包解到客户端目录的 `host/`，亦可使用现有 `PCL_HOST_ASSEMBLY` / `PCL_DOTNET` 配置独立 Host。

## 签名与兼容

统一清单目前是发布产物索引，**不能作为自动更新的信任依据**。SHA256 只能与可信清单配合校验完整性。生产发布需完成平台签名/公证，再重新归档计算哈希。

Host 自动更新沿用 [Host 更新接入](Host自动更新与接入.md) 中的 `Pcl.UpdatePack`：完成平台签名后生成 `host.zip` 及带 RSA-PSS 签名的 `feed.json`，上传不可变 HTTPS 地址，并在客户端签名前放入真实公钥/策略。统一清单中的 Host ZIP 与该工具输出不能仅凭同名互换；签名 feed 的长度、哈希及逐文件清单必须对应最终实际下载的字节。

当前参考客户端要求协议 1、data epoch 1 和 `desktop.contract-only.v1`；打包器拒绝不兼容 Host、发布版本不一致、混入核心的客户端、目录链接、特殊文件与大小写冲突。Contract 随各自包携带。客户端自更新、内容外置与正式签名频道接通仍是后续阶段。

## 验证与候选流水线

```bash
python3 scripts/test-component-packages.py
```

定向测试覆盖包内容隔离、完整包组合、哈希/大小、可执行位、可重复归档、版本/兼容拒绝、输出隔离与链接拒绝。现有真实 Host 合约和签名更新测试继续承担协议、候选切换与回退验证；修复前后源码组合的本机验证见下文；这不等同于任意历史版本兼容承诺。

[候选流水线](../.github/workflows/component-packages.yml) 在 Mac runner 构建原生资产、独立发布两包、验证 ZIP 完整性、解压后实际交付的 Core 日志修复与真实 Host 合约，再上传候选；不自动发布 GitHub Release，不持有生产签名私钥。正式签名、不可变上传和客户端策略配置需在发布环境接线。

## 修复合入前的本机结果（2026-11-01，历史记录）

基线 `a57c34e`，开发分支 `feat/component-packages`。Apple Silicon Mac 自包含发布完成，架构守卫检查 3130 个方法、51526 次符号使用，0 违规。客户端约 43.66 MiB，Host 约 33.20 MiB，组合包约 76.87 MiB；精确大小与 SHA256 见本地生成的 `artifacts/components-0.42.0-osx-arm64/packages/release-manifest.json`。

5 组定向打包测试通过。将组合 ZIP 解到新目录并恢复 ZIP 中记录的 Unix 执行权限后，使用本轮编译的独立最小客户端测试连接其中的自包含 Host，28 项合约断言通过，报告为 `artifacts/component-contract-unrestricted.json`。本机沙箱限制私有管道创建，因此这项进程通信验收在沙箱外、全新隔离数据根运行；没有使用个人账户或游戏目录。

这些结果证明本机部署目录与真实 Host 合约可用，不代表完整 GUI、游戏启动、新旧客户端版本组合、三平台发布或在线签名更新源均已验收。候选流水线已编写，尚未在远端运行。流水线使用的 Mac runner 标签依据 [GitHub runner 文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)。


## 修复基线复核（2026-11-01）

已将远端 main 的 `81016b476e8811ecbfbd3f969d143b646ac5282d` 快进合入 `feat/component-packages`，保留全部本地分包改动。该提交修复 Unix 独立日志脱敏/16 MiB 上限及 macOS 钥匙串写入前 65,536 UTF-8 字节边界。Client、Contract 与 Desktop 的上游源码没有改变，分包属性无冲突。

### 对分包的影响

- `Pcl.Core` 新增内嵌原生辅助程序，必须重新构建完整 Host；不需要新增独立用户下载块，也不应把该程序从 Core 中剥离后单独替换。
- Unix 构建需要 `cc`，构建入口增加了前置检查；支持用 `PCL_COMPONENT_OUTPUT` 保留历史产物并另建修复后目录。
- 重新构建后的三个 ZIP 哈希均发生变化，旧清单不能用于新字节。客户端源码未变不等于构建产物逐字节相同；本轮以实际归档哈希为准。
- `BundleHost=false` 仍得到不含 Core/Host 的客户端；完整部署包仍含 `host/`。原完整 `.app` 构建入口保持默认捆绑 Host，但本轮没有重新执行 GUI 或 Developer ID 签名/公证验收。
- 仍使用 0.42.0 / sequence 42000 作为开发验证元数据。**正式发布这些不同字节前必须递增 Host 序号并确定新发布版本，不得覆盖已经发出的同序号签名清单或旧发布资产。** 当前没有接通生产更新源。
