# 仓库结构与更新分块

本分类以 0.42.1 本地 build 424 的源码、项目引用及发布脚本为准，核心基线为 `81016b4`。**开发按职责分组件，更新按经过兼容验证的一组组件交付。** 分类用于定位代码和确定交付范围，不表示五种独立更新包都已实现，也不要求移动现有目录。

## 一、五类更新与交付内容

| 分类 | 包含内容及源码入口 | 当前实现 | 交付方式与后续要求 |
|---|---|---|---|
| 客户端包 | [Desktop](../src/Pcl.Desktop/)、[Client](../src/Pcl.Client/)、匹配的 [Contract](../src/Pcl.Contract/)、界面资源及 [Native](../src/Pcl.Native/) 窗口桥接 | Avalonia Mac 参考客户端；Client/Contract 也供独立最小客户端使用。已实现 Mac ARM64 客户端签名更新、退出替换与失败回退，见[本地自更新阶段](0.42.1-客户端自更新.md) | 客户端与配套通信库、资源整体发布；不能只替换一个 DLL。新页面依赖新能力时与 Host 协调兼容 |
| Host 核心包 | [Host](../src/Pcl.Host/)、[Application](../src/Pcl.Application/)、[Domain](../src/Pcl.Domain/)、[Ports](../src/Pcl.Ports/)、[Core](../src/Pcl.Core/)、匹配 Contract，以及必要的 [Legacy](../src/Pcl.Legacy/)、[vendor](../vendor/) 和运行依赖 | 独立 Host 与可配置的签名自动更新已经实现；默认官方签名频道未配置 | 按操作系统/CPU 架构整体构建、验证和发布；Domain/Application/Core 等内部 DLL 不供用户自由组合 |
| 数据与内容包 | 百科索引、项目映射、兼容表、帮助、语言和主题等适合外置的内容 | 百科/映射已支持签名外置包、兼容检查、回退及客户端自动检查/手动安装入口；其他内容仍按原方式管理 | 百科/映射使用格式 1、递增序号和固定公钥，Host 下次启动生效；见[数据分包](0.42.1-数据分包.md)。其他内容外置仍需分别定义格式与迁移 |
| 外部工具与运行环境 | 游戏 Java、EasyTier 等外部进程及其运行文件 | 已有按元数据/固定版本获取与校验路径；自动 Java 与 EasyTier 的现有路径限定 Apple Silicon Mac | 按工具版本、平台和校验信息管理，不跟随任意核心 DLL 替换；平台支持逐项验收 |
| 开发与验证工具 | [tests](../tests/)、[scripts](../scripts/)、[tools](../tools/)、[examples](../examples/)、[CI](../.github/workflows/core-ci.yml) | 控制台测试、架构守卫、构建/审计脚本、更新签名工具和最小客户端示例 | 随源码维护，通常不进入用户更新包；工具生成的运行资产可能进入产品，示例也可按需独立部署 |

### 当前物理包与分类的区别

[build-handoff.sh](../scripts/build-handoff.sh) 依次调用原生桥构建和 [build-release.sh](../scripts/build-release.sh)。后者仍生成包含参考客户端及完整 `host/` 子目录的自包含 Mac `.app` 和 ZIP，并复制许可/声明。因此，**客户端包 + Host 核心包是兼容与部署边界，原有发布脚本保留完整安装包；新增独立分包、签名发布和基线校验入口见[0.42.1 分包交付](0.42.1-分包交付.md)**。

Host 更新器可将候选安装到独立版本目录，在空闲或下次启动时切换，并在启动/握手失败时回退；不覆盖签名 `.app` 内部文件。启用需要发布者配置可信公钥与更新源。它不更新 UI、不进行数据格式迁移，也不提供运行时代码热替换。详见[Host 更新接入](Host自动更新与接入.md)。

Contract 随客户端与 Host 分别携带匹配版本，通过协议版本、能力和数据约定判断兼容；不能让用户单独更新 Contract。客户端 .NET 版本与 Host 包内的 .NET 运行依赖也属于各自部署约束：自包含包携带运行时，framework-dependent 包要求部署环境已有兼容 .NET；这与游戏 Java 是两种运行环境。

| 资产 | 当前归属与处理 |

| `artifacts/native/lwjgl-unsafe-agent-2.0.jar` | 固定版本、校验哈希的游戏兼容运行资产，当前也被项目复制；不是需要向用户交付的开发工具本体 |
| `vendor/PCLCS/Resource/WikiEntries.txt` | 上游百科/项目映射的原始输入，保留嵌入 PCLCS 作为离线回退，可导出为[独立数据包](0.42.1-数据分包.md)；新身份规则在 Domain，数据转换在 Core，不在 vendor 增加页面或网络控制器 |
| `src/Pcl.Core/Compatibility/` | 当前嵌入 Core 的兼容数据；将来是否独立更新需先定义格式与程序兼容约束 |
| `docs/windows-layout-baseline.json`、`docs/data/PCL2完整功能矩阵.json` | Desktop 当前嵌入的布局/追踪资源；不因目录叫 docs 就从构建输入中排除 |
| `docs/data/feature-status-overrides.json` | 人工审核输入，不是运行时内容更新包或可删除缓存；详见[数据说明](data/README.md) |
| `artifacts/verification-*` | 已跟踪的历史验收证据，保留原位置和哈希；不当作本轮测试结果或用户更新内容 |
| 许可、NOTICE、作者署名与劝导 | 跨所有交付块的要求；按实际包含的内容随包分发，不能归入“仅开发工具”后省略 |

## 二、开发组件与职责

| 目录 | 职责 | 所属交付块/注意事项 |
|---|---|---|
| `src/Pcl.Desktop` | 页面、控件、主题、导航与窗口交互 | 客户端；仅引用 Client/Contract/Desktop.Updates；不再构建 Host 或架构守卫 |
| `src/Pcl.Client` | RPC、订阅、重连、客户端会话；可选 Host 部署更新 SDK | 客户端；更新 SDK 不复制安装/登录业务 |
| `src/Pcl.Contract` | 请求、结果、事件、错误、能力与公开接口 | 客户端/Host 各自匹配携带 |
| `src/Pcl.Host` | 进程入口、组合根、会话、数据根锁、空闲退出及构建身份 | Host 核心包 |
| `src/Pcl.Application` | 受理、进度、取消、恢复、生命周期与用例编排 | Host 核心包 |
| `src/Pcl.Domain` | 纯规则、依赖/兼容约束与计划 | Host 核心包；不引用 Ports，不隐式访问外部系统 |
| `src/Pcl.Ports` | 文件、下载、凭据、进程等外部能力接口 | Host 核心包；可引用 Domain |
| `src/Pcl.Core` | Adapter 与仍在使用的安装、下载、事务、资源和进程实现 | Host 核心包；新增纯规则优先 Domain，迁移按用例推进 |
| `src/Pcl.Legacy` | 仍被调用的旧规则兼容代码 | Host 所需依赖，不能因名称含 Legacy 就删除 |
| `vendor/PCLCS`、`vendor/MeloongCore` | 上游数据格式、类库与基础能力 | 按实际依赖进入 Host；遵守各自许可及目录维护说明 |
| `src/Pcl.Native` | 当前 macOS 原生窗口桥接 | 原生运行依赖，复制范围见上表 |
| `src/SharedProtocol` | 按项目链接编译的共享通信实现 | 源码共享；不将所有公共类型迁入此目录 |
| `src/Pcl.Cli` | 通过 Host 运行的命令行客户端 | 只引用 Client/Contract |
| `src/Pcl.Desktop.Updates` | Mac 应用退出替换、签名校验与回退 | 客户端及更新助手共享，只引用 Contract |
| `tools/Pcl.CoreDiagnostics` | 原同进程诊断和旧业务命令 | 开发工具，允许引用 Core/Application；不属于客户端 SDK |
| `examples/Pcl.MinimalClient` | 仅 Client/Contract 的独立接入示例 | 示例默认随源码；可单独部署完整客户端目录 |

调用关系见[架构与设计取舍](架构与设计取舍.md)，约束以[架构规范 v1.5.3](architecture/PCL-Mac架构规范.md)为准。界面表达用户意图，Host 一侧重新进行权威校验并实际执行。当前没有通用动态插件加载系统。

## 四、添加功能时放在哪里

| 需求 | 主要修改位置 |
|---|---|
| 按钮、布局、主题、窗口行为 | Desktop；需要系统窗口能力时修改 Native |
| 为已有能力增加展示入口 | Desktop，必要时补 Client 封装 |
| 模组兼容、依赖或版本选择规则 | Domain；由 Application/Core 获取并提供输入，复用现有规则与事务 |
| 新模组下载来源 | Core 适配器；确需新增抽象时补 Ports |
| 带进度、取消、恢复的操作 | Application + Core；涉及新客户端调用时补 Contract、Host、Client |
| 新操作系统能力 | Ports + 平台适配实现 + Host 接线 |
| SwiftUI 或其他新界面 | 新客户端，通过协议复用 Host，不复制核心业务 |
| 上游解析或基础库问题 | 对应 vendor；保留来源、遵守维护说明并限制补丁范围 |

先判断是否属于组件原有职责。搜索筛选控件属于 Desktop，“哪些版本符合实例”的权威判断属于核心；UI 输入提示不能替代 Host 校验。不得为了一个页面在 UI 创建另一套下载器、依赖求解器或安装事务。

## 五、新功能的推荐流程

以接入新的模组来源为例：

1. 明确用户行为与验收标准：查询、分页、版本选择、来源失败提示、安装取消和数据写入范围。
2. 检查复用点：优先沿用搜索会话、候选选择、依赖规划、幂等操作和安装事务。
3. 按职责实施：Core 接 API，Domain 计算纯规则，Application 编排，Host 组装；当前迁移中的既有 Core 入口逐步整理，不一次性搬迁整个项目。
4. 仅在需要新信息/操作时扩展 Contract，同步 Client/UI；使用能力标识处理新旧 Host 兼容，不能默默假定对方已升级。参见[客户端接入指南](客户端接入指南.md)。
5. 验证规则、协议与真实入口，覆盖失败、取消、重复请求、文件写入和恢复；平台相关变动在对应系统验收。测试分清 fixture、真实服务、UI、游戏菜单和世界保存。
6. 按交付范围发布：兼容后台变更可只更新完整 Host；新页面与新协议协调更新客户端/Host；数据格式变化先设计迁移、备份和回退，再决定是否允许自动更新。

修改文档或分类不会自动触发版本升级、安装包重发或功能矩阵状态变更。具体构建/测试入口见[开发与验证](开发与验证.md)，当前缺口见[技术债](architecture/技术债.md)与[剩余清单](剩余清单.md)。

当前本地 build 424 的发布接线与清理策略见[统一更新与清理](0.42.1-统一更新与清理.md)。
