# 分包构建与签名

当前发布身份、平台范围与限制以根目录 README 和 release.json 为准。本文说明开发机制；本版默认手动升级，不配置测试或生产更新策略。

## 交付范围

| 产物 | 内容 |
|---|---|
| 客户端 ZIP | Desktop、Client、配套 Contract、运行时、界面/原生资源与许可；不带 Host/Core |
| Host ZIP | Host、Application、Domain、Ports、Core、Legacy、配套 Contract、必要上游库与自包含运行时；内含日志辅助程序 |
| 完整部署 ZIP | 客户端加 `host/`，供部署组合使用 |
| Mac `.app` ZIP | 仍保留首次安装的完整客户端与 Host；平台签名后归档，验证 AppleDouble、文件权限及解压后的深度签名 |
| 统一清单 | 版本、平台、核心来源提交、包长度/哈希/下载地址、协议/能力/数据 epoch、Host 序号及签名引用 |
| 签名发布产物 | RSA-PSS/SHA256 的 Host feed、统一清单签名、公开密钥、校验和，以及嵌入客户端/安装器的固定公钥更新策略 |

客户端与 Host 分别携带 Contract，不提供单独 DLL 拼装。百科索引与项目映射已支持独立签名包；其他内容和外部工具仍按既有方式管理。客户端包已能单独交付；支持退出后替换和回退，见[客户端自更新](客户端自更新.md)。

## 基线与版本规则

今后的分包任务先取得远端最新 `main`，再更新 `release.json` 中的 `coreVersion` / `coreCommit`。版本使用 **0.[最新核心次版本].1**；本轮即 0.42.1。Host 序号必须严格高于已发布候选，且与 `release.json.hostSequence` 一致；不能覆盖同序号的已签名资产。

```bash
git fetch origin main
python3 scripts/verify-core-baseline.py --upstream-ref origin/main
```

校验器比较核心、Host、Contract、共享协议、原生源码及 vendor 的实际内容。Host 项目中的 Version / HostUpdateSequence 作为分包元数据不同；另允许 release.json.contentIntegration 固定的八个数据/Host 更新适配文件，逐文件校验基线及集成后的 SHA-256；拒绝未跟上最新核心、基线标注错误及未经纳入核心基线的新核心文件。Windows 文本换行转换不算核心改动。离线构建检查已记录基线；流水线额外检查最新上游。

## 构建与独立部署

```bash
# Mac 客户端/Host/完整部署包
bash scripts/build-native.sh
DOTNET=/path/to/dotnet bash scripts/build-components.sh osx-arm64

# 只构建 Host，不构建 Desktop/Client
DOTNET=/path/to/dotnet bash scripts/build-host-package.sh osx-arm64
```

Unix 需要匹配目标平台的 C11 `cc`。独立 Host 流水线分别在 Mac arm64、Linux x64、Windows x64 上运行；不把核心包成功等同于这些平台的完整游戏图形支持。新输出目录必须为空，重跑可分别设置 `PCL_COMPONENT_OUTPUT`、`PCL_HOST_PACKAGE_OUTPUT`、`PCL_RELEASE_OUTPUT`。

纯客户端连接外部自包含 Host，无需另装系统 .NET：

```bash
PCL_HOST_EXECUTABLE=/absolute/host/Pcl.Host /absolute/client/PCL-MacPort
```

原 `PCL_HOST_ASSEMBLY` + `PCL_DOTNET` 的 framework-dependent 接入保留；完整安装使用默认随包 Host。客户端路径及数据根继续决定更新存储作用域，不更改个人账户或游戏目录。

## 签名发布与更新源接线

`component-publisher.yml` 是手动调用的可信发布工作流。配置 `component-publishing` 环境中的 `COMPONENT_SIGNING_PRIVATE_KEY`，输入不可变 HTTPS 资产目录和此平台/频道的稳定 feed URL。工作流生成已验签候选附件，不自动创建公开 Release 或覆盖在线更新源。

本地等价入口：

```bash
dotnet build tools/Pcl.UpdatePack/Pcl.UpdatePack.csproj -c Release
python3 scripts/sign-component-release.py \
  --work artifacts/components-0.42.1-osx-arm64 --release release.json \
  --key /secure/publisher.pem --dotnet /path/to/dotnet \
  --tool tools/Pcl.UpdatePack/bin/Release/net10.0/Pcl.UpdatePack.dll \
  --output /fresh/signed-release \
  --base-url https://publisher.example/releases/0.42.1/osx-arm64 \
  --feed-url https://publisher.example/preview/osx-arm64/feed.json
```

上面的域名仅为配置示意，必须换成发布者真实地址。工具拒绝把私钥放进输入/输出资产目录。它在客户端归档前写入固定公钥策略，再生成和验签统一清单。Host ZIP 直接使用 `Pcl.UpdatePack` 的结果，保证索引与签名 feed 对应相同字节。旁附公钥用于审计，客户端的信任根来自预先随包固定的策略，不能信任任意下载包带来的新公钥。

签名流程产生的策略也必须在 `.app` 签名前注入：

```bash
PCL_HOST_UPDATE_POLICY=/fresh/signed-release/host-update-policy.json \
DOTNET=/path/to/dotnet bash scripts/build-release.sh
python3 scripts/add-component-installer.py /fresh/signed-release \
  artifacts/Plain-Craft-Launcher-Refactoring-0.42.1-macOS-arm64.zip \
  /secure/publisher.pem /path/to/dotnet \
  tools/Pcl.UpdatePack/bin/Release/net10.0/Pcl.UpdatePack.dll
```

附加安装器前检查应用版本与固定公钥策略一致，再更新并重签统一清单。公开上传时先上传不可变包及清单，核对可下载字节，最后将平台 Host feed 发布到策略中的稳定地址。清单有效期沿用工具的 30 天策略，需运营刷新；即使 feed 过期，既有已安装版本仍可离线启动。

仓库没有内置生产私钥、默认官方更新地址或临时测试信任根。PR 流水线只使用一次性测试密钥，测试签名包不作为正式候选附件上传。当前 Mac 签名仍是 ad-hoc，未声明 Developer ID 公证。正式线上频道启用需要发布者提供上述密钥和托管配置。
