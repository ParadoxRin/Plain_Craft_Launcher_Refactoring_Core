# 项目维护边界

当前发布身份、平台范围与限制以根目录 README 和 release.json 为准。本文说明开发机制；RC 默认手动升级，不配置测试或生产更新策略。

这里的 PCLCS 指整个核心产品；`vendor/PCLCS` 是保留来源和许可的上游兼容依赖，不等于整个产品。

## 职责与依赖审查

| 模块 | 应承担的职责 | 审查结果及本轮处理 |
|---|---|---|
| Domain / Ports / Application | 纯规则、外部能力接口、业务用例编排 | 已有独立项目，保持现有依赖；不重新搬回 Core，也不为拆分新增通用 Kernel |
| Core / Legacy / vendor | 既有执行实现、平台适配、兼容代码与必要上游库 | 保持一个经过验证的后端实现集合，不把内部 DLL 当作客户端插件 |
| Host | 组合根、进程与数据目录所有权、公开协议服务 | 可独立构建；不引用任何客户端或 UI 库 |
| Contract / Client | 公共 DTO、协议与可选 .NET 客户端接入实现 | 原 Client 混入 Mac 应用自身更新器；现移出，并提供仅含 Contract/Client 的独立 SDK 包 |
| Desktop | Mac 图形交互和客户端生命周期 | 原本构建时仍引用并复制 Host；现删除这些构建依赖，由安装器脚本显式组合两端 |
| CLI | 经公开接口接入 Host | 原本混合远程入口和直接构造 Core 的旧命令；现正式 CLI 仅引用 SDK，旧命令迁入独立诊断工具 |
| 开发工具 | 签名、测试、诊断和架构检查 | 不伪装成客户端；整仓架构检查在集成流程执行，不成为客户端编译前置条件 |

运行时调用仍是：客户端 → Client/Contract → 独立 Host → Application / Core → Domain / Ports / Adapters。凭据留在 Host，客户端不直接初始化业务服务。

## 已完成的源码与项目拆分

1. `src/Pcl.Desktop.Updates`：从 Client SDK 实际迁出 Mac 自更新源码。它只引用 Contract，Desktop 和外部更新助手显式引用此项目。SDK 消费者不再携带 Mac 应用替换、bundle 检查和应用路径规则。
2. `src/Pcl.Desktop`：移除对 Host 和整仓 ArchitectureGuard 的构建引用、Host 复制目标。构建 UI 不再构建后端；完整安装器仍可由 `build-release.sh` 显式发布 Host 后组装。`build-components.sh` 同样分别发布并进行完整 IL 架构检查。
3. `src/Pcl.Cli`：仅保留 `host-status`、`host-install`、`host-launch` 远程命令，要求显式 Host 和数据根。它不引用 Core/Application，不从源码目录猜测 Host 位置。原本的 962 行同进程入口及相关诊断实现迁入 `tools/Pcl.CoreDiagnostics`，未删除其功能。旧验收脚本已更新到诊断工具路径。
4. SDK：`build-client-sdk.sh` 生成本地 `Pcl.Contract` 与 `Pcl.Client` NuGet 包，附许可、使用说明和哈希清单。客户端项目可在源码引用与 `UsePclSdkPackages=true` 包引用之间选择；协议 DTO 命名和线格式保持不变。
5. 客户端独立工作区导出：只复制客户端、独立更新模块、必要界面资源/原生资产、最小客户端测试及 SDK 二进制包。不复制 Core、Host、vendor、SDK 源码或 Git 元数据。该工作区可在没有核心源码时编译、发布和连接外部 Host。

6. 核心独立工作区导出：`export-core-workspace.py` 先验证最新核心基线，再导出 Host 后端源码闭包及必要上游许可和哈希清单；不包含 Desktop、Client 传输实现或 CLI。Contract 留在核心作为协议定义，协议调整仍需同步 SDK 兼容验证。

## 独立维护入口

| 入口 | 范围 |
|---|---|
| `PCLCS.Core.slnx` | Host 及其后端项目依赖，不包含 Desktop/Client SDK 实现 |
| `PCLCS.ClientSdk.slnx` | Contract 与 Client，不包含后端和任何客户端 UI |
| `PCLCS.Clients.slnx` | Desktop、远程 CLI、最小客户端及必要客户端侧组件 |
| `PCLCS.Tools.slnx` | 后端诊断、数据/签名工具、客户端更新助手 |
| `PCL-MacPort.sln` | 保留原整仓集成入口，包含新项目，不再作为唯一维护方式 |

```sh
python3 scripts/export-core-workspace.py --output /absolute/fresh-core-workspace
dotnet build /absolute/fresh-core-workspace/PCLCS.Core.slnx -c Release
DOTNET=/absolute/dotnet bash scripts/build-client-sdk.sh /absolute/fresh-sdk-feed
python3 scripts/export-client-workspace.py --output /absolute/fresh-client-workspace --sdk-feed /absolute/fresh-sdk-feed
dotnet build /absolute/fresh-client-workspace/Clients.slnx -c Release
PCL_HOST_EXECUTABLE=/absolute/host/Pcl.Host dotnet /absolute/fresh-client-workspace/src/Pcl.Desktop/bin/Release/net10.0/PCL-MacPort.dll
```

独立客户端仍需通常的 .NET/Avalonia 依赖和匹配平台原生文件；“没有核心源码依赖”不是“没有任何构建依赖”。SDK 包不上传公共源。`check-module-boundaries.py` 同时检查运行与构建引用，不能用 `ReferenceOutputAssembly=false` 偷渡 Host；负例测试覆盖这种构建耦合、CLI 直连 Core 及跨模块源码链接。整仓 IL 守卫继续检查真实类型使用和 Domain 纯度。

## 接入边界与后续事项


- 多个客户端实现均可接入同一套核心协议，但**同一数据根仍保持单一写入会话**。这次没有放开并发写入或改成多租户服务。
- Core 中现有适配器、兼容执行代码仍有可进一步按业务用例整理的空间；不能仅凭目录名称或 DLL 数量断言所有职责已完全纯化。其继续拆分需要对应 Ports 与用例测试，不在本轮做无行为收益的搬家。
- 本轮完成同仓模块与客户端可导出边界；没有创建多个远端仓库。拆成多个 Git 仓库、正式 SDK 发布、跨语言 SDK 与公开兼容维护周期仍需要单独确定。
- 完整 `.app` 仍可携带首次运行所需 Host，这是安装器组合方式，不再是客户端的源码/构建依赖。安装布局迁移、正式 HTTPS 更新源和其他数据/工具分包仍属于独立后续事项。
- 不要求先做 Windows/Linux UI 或重写现有 Mac 客户端才能认定核心/客户端维护边界成立；其他平台运行能力需单独实际验收。
