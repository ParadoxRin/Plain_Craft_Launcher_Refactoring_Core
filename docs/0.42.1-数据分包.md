# 0.42.1 本地后续：百科与项目映射数据包

本阶段仅在本地完成，不推送 GitHub、不配置正式更新源。应用仍为 **0.42.1**，build **422**，Host 序号 **42101**，与第一阶段的 build 421 / Host 42100 区分。核心基线仍是 `81016b476e8811ecbfbd3f969d143b646ac5282d`，保留日志脱敏/限长和 macOS 钥匙串写入边界修复。

## 已实现的行为

- 百科搜索和跨站项目身份映射共享一份进程级数据快照。更新在 **Host 下次启动**时生效，既有搜索会话不会半途切换索引。
- 保留内置 PCLCS 词库作为首次启动及故障回退；外置包无需重建 Host。上游 27,262 条记录完整导出，包括多项目百科页和 243 条含特殊字符的旧项目名。词库中的名称只是数据，实际下载仍使用原有标识校验和 Domain 一对一身份规则。
- 格式 1 的 `wiki-project-index` 数据包同时包含标题、百科 ID、两站 slug、热度、序号、频道、来源与适用 Host 版本范围。仅承载 JSON 数据，不接受程序集、脚本或档案解压入口。
- 使用 RSA-PSS/SHA256 验签；独立固定公钥来自随 Host 配置的策略，不信任下载附件自带的公钥。包上限 16 MiB，最多 100,000 条记录。
- 安装写入内容寻址文件，再原子更新选择状态；并发安装通过文件锁互斥。新包序号必须严格递增。显式回退保留最高序号，避免旧包重复安装。
- 读取时重新验哈希、签名、频道、格式与 Host 兼容范围。当前包损坏先尝试上一包，两者无效则使用内置索引。状态文件损坏时允许内置读取，但拒绝继续安装，避免静默清空防重放记录。
- 修正纯客户端发布中构建依赖的 Host / ArchitectureGuard 启动器与运行时元数据残留；打包器现在拒绝这些文件。

没有删除上游嵌入资源；兼容表、语言、主题、外部 Java/EasyTier 继续按原方式管理。本数据阶段 build 422 不包含客户端自更新；后续 build 423 的实现和独立验收见[客户端自更新](0.42.1-客户端自更新.md)。

## 基线与集成差异

`release.json.contentIntegration` 明确列出五个文件：两个 Core 内容适配文件，以及百科读取、身份投影接线和离线索引说明。每个文件记录基线 SHA-256（新增文件为 null）和当前 SHA-256。基线检查同时核对两侧哈希，不能用目录豁免绕过最新核心检查；上游相同文件发生变化时必须重新审查集成。原有 Domain、Application、Ports、Contract、vendor 及日志/凭据实现均不修改。

独立客户端/Host 的清单中同时保留核心提交和集成哈希，避免把带适配增量的 Core 描述成完全未经修改的原始核心。

## 构建数据包

先构建管理员/发布者工具（不需要把工具及其 Core 依赖放进纯客户端）：

```bash
dotnet build tools/Pcl.ContentPack/Pcl.ContentPack.csproj -c Release
python3 scripts/build-content-release.py \
  --dotnet /path/to/dotnet \
  --tool tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll \
  --key /secure/content-publisher.pem \
  --sequence 1 --min-host 0.42.1 --max-host 0.42.99 \
  --output /fresh/content-release
```

默认导出当前内置词库；自定义 `--rows` 必须同时用 `--provenance` 写明真实来源，并经过发布者内容审查。工具不检查百科内容是否最新，不根据名称推断新的跨站关系。输出含签名 JSON、携带上游许可的分发 ZIP、公开策略及校验清单。私钥不得位于输出目录。ZIP 用于分发与许可审计，运行时安装的是其中已签名的 JSON。

策略 `content-update-policy.json` 只有 `Channel` 与 `PublicKeyPem`。将发布者确认过的策略固定在 Host 旁边，并在平台签名/Host 包签名前注入：

```bash
PCL_CONTENT_POLICY=/trusted/content-update-policy.json \
DOTNET=/path/to/dotnet bash scripts/build-components.sh osx-arm64
```

`build-host-package.sh`、`build-release.sh` 同样支持此配置。未配置策略时只使用内置索引。测试密钥产物仅为本地夹具，不能作为生产更新信任根。

## 安装、检查与回退

```bash
dotnet tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll \
  install /absolute/content-store /trusted/content-update-policy.json 0.42.1 \
  /downloads/pcl-wiki-project-index-1.json

# 显式下载：HTTPS、禁用重定向、总计 60 秒及 16 MiB 上限，随后同样验签再安装。
dotnet tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll \
  fetch /absolute/content-store /trusted/content-update-policy.json 0.42.1 \
  https://publisher.example/content/pcl-wiki-project-index-2.json

dotnet tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll \
  status /absolute/content-store /trusted/content-update-policy.json 0.42.1
dotnet tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll \
  rollback /absolute/content-store /trusted/content-update-policy.json 0.42.1
```

通过 `PCL_CONTENT_ROOT` 给 Host 指定同一绝对目录；`PCL_CONTENT_POLICY` 可显式指定预置策略。未指定目录时，Host 使用系统 `LocalApplicationData/PlainCraftLauncherRefactoring/content/wiki-project-index`。不同发布者或频道应指定独立目录。不要把账户/实例目录当作内容存储目录。

这里的 Host 版本是安装时的兼容预检，Host 启动时仍用自身程序集版本重新检查。本 build 422 阶段的管理员工具并不替代客户端 UI；后续 build 424 已加入自动检查和数据更新按钮，见[统一更新与清理](0.42.1-统一更新与清理.md)。`fetch` 的正式 HTTPS 托管访问未验收。

## 与统一发布清单衔接

在 `sign-component-release.py` 原参数之外加入：

```bash
--content-release /fresh/content-release \
--content-tool tools/Pcl.ContentPack/bin/Release/net10.0/Pcl.ContentPack.dll
```

发布器使用待打包 Host 中的固定内容策略校验数据签名和版本，随后将数据 JSON 与带许可的 ZIP 纳入统一签名清单。数据包本身不限定 CPU/系统；具体 Host/客户端仍按平台交付。`verify-component-delivery.py` 使用实际解包 Host 的 Core 再次校验内容包，不能只凭发布器构建目录验收。
